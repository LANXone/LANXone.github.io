🧠 第 1 页：一张图看懂编译

三个必须记住的认知：

# 认知 意义
1 g++ 只是个调度器，自己什么都不干 它按你的参数依次调用 cpp → cc1plus → as → ld。用 g++ -v 你能亲眼看到
2 编译器只认文件，不认"工程" IDE 帮你做的事 = 写好参数 + 调 g++ + 把产物放好。你手写命令行，一点没损失
3 编译期环境和运行期环境是两批文件 头文件/库文件是编译期；DLL 是运行期。混淆这点是"我机器上能跑、拷给别人就崩"的根源

编译期 vs 运行期，需要哪些东西

阶段 需要 缺了会怎样

📦 第 2 页：下载 MinGW（选对版本）

为什么需要它

Windows 自带没有 C++ 编译器。要编译就得装一个工具链。GNU 这一套叫 MinGW（微软自己那套叫 MSVC，两者的库不能混用）。

两种分发方式，选哪个

方式 是什么 选它吗
WinLibs 独立 zip 一个 zip，解压即用，像绿色软件 ✅ 本文用这个，零概念负担
MSYS2 包管理器 + Unix 环境 以后要装很多库时用（见第二篇）

下载步骤

  1. 打开 https://winlibs.com/
  2. 找 UCRT runtime 那一组（版本越新越好，如 GCC 14.x / 15.x）
  3. 文件名长这样，认准四个片段：
片段 该选什么
x86_64 ✅ 64 位
posix ✅ 必须。老的 win32 变体不支持 C++ 多线程
seh ✅ 异常用 Windows 原生机制，比 sjlj 好
ucrt ✅ 新运行时
llvm / dwarf ❌ 那是 LLVM 后端，命令变成 clang++

❌ 别下错

错误选择 后果
MSYS2 的 .sfx.exe 安装包 不是本文路线
名字带 llvm 命令是 clang++，不是本文目标
SourceForge 上的 MinGW 3.x（2011 年） C++11 之后特性大面积缺失

下载慢的话：搜 "winlibs 镜像"，或用 GitHub niXman/mingw-builds-binaries 的 Releases。

为什么用用户变量不用系统变量？
用户变量：只对你生效、不需管理员权限、改错无风险 → ✅ 首选
系统变量：全机器共享、要管理员权限 → 不必要

验证 + 处理冲突

输出 含义

"我装了 VS 所以我的 MinGW 程序一定能跑"是错的，反之亦然。

🔧 第 7 页：编译命令详解

最简 & 日常标准命令

选项 作用 为什么
-std=c++20 语言标准 不写则用很老的默认值，for (auto& x : v)、智能指针会报错
-O2 优化 发布用。调试必须换成 -O0
-Wall -Wextra 警告 不是错误，但每条都在提醒你有坑
-g 调试信息 没有它 gdb 里看不到变量名和源码行号

编译并运行（一条龙）

💡 用 && 不用 ; —— && 是"前一条成功才执行后一条"。
用 ; 会在编译失败时去运行上次的旧 exe，这是新手常见的困惑来源。

-std= 怎么选

标准 状态 建议
C++11 成熟 保底（老库只支持到这）
C++17 主流 ✅ 兼容性最好，第三方库支持最全
C++20 主流 ✅ 新项目推荐（ranges、format、协程）
C++23 逐步落地 尝鲜

📤 第 14 页：把 exe 发给别人

最省事：静态化 + 剥离符号

清单

  • [ ] 架构匹配：你编的是 x64，对方必须 64 位 Windows。g++ -m32 编 32 位（但 MinGW 32 位支持少）
  • [ ] 别用 -march=native —— 只能在你的 CPU 上跑
  • [ ] 确认无外部依赖：objdump -p app.exe | grep "DLL"
  • [ ] 杀毒误报：MinGW 编的程序偶尔被杀软当"未知程序"。加版本信息资源（windres）、代码签名、或分发 zip 会好很多
  • [ ] 控制台 vs GUI：加 -mwindows 就没有黑框，但不能直接用 std::cout（没有 stdout），需要 AllocConsole() 或写日志文件

为什么不能混

ABI（应用二进制接口）包括：参数传递方式、结构体内存布局、C++ 名字修饰规则、异常机制、std::string/std::vector 的内部实现。

MSVC 和 GCC 的 ABI 完全不同，混用会导致参数传错、行为诡异、运行崩溃。

判断库是哪个编译器编的

MinGW-w64 (GCC) MinGW 构建 x64-mingw-dynamic / x64-mingw-static xxx-mingw.zip
MSVC (cl.exe) MSVC 构建 x64-windows-dynamic / x64-windows-static xxx-VC.zip

一句话记忆：-mingw 结尾 = 给 MinGW；-VC 结尾 = 给 MSVC。

兼容性技巧：纯 C 接口

用 extern "C" 的纯 C 接口 ABI 差异会小很多（无重载、无 mangling）。
但结构体 padding/对齐规则仍可能不同 → 最安全还是全套统一。

# 要点 内容
1 三样东西三个期 头文件（编译期）+ 库文件（链接期）+ DLL（运行期），缺一不可
2 分层诊断 -I 管头文件、-L/-l 管库、拷 DLL 管运行。一次只查一层
3 -fsyntax-only 是你的诊断利器 把"头文件找不到"和"库找不到"分开，一次解决一个
4 链接顺序：使用者在前 有疑问用 -Wl,--start-group ... -Wl,--end-group
5 ABI 必须统一 MinGW 程序配 MinGW 库，别混 MSVC
6 优先用包管理器 vcpkg / MSYS2 / apt / brew。手动维护路径是长期痛苦
7 偷看工具怎么算参数 cmake --build build --verbose、pkg-config --cflags --libs xxx

🎯 一句话总结：
用命令行手敲一遍，你就知道每个 -I -L -l 到底在干什么。

SDL的各个部分

SDL库目录结构说明（Windows）

路径：C:\ccccc\GANME\SDLproject\SDL
解压后的SDL开发包，4个核心文件夹：bin、include、lib、share

bin

存放SDL运行时动态库文件（.dll）

  • 里面是 SDL2.dll（64位/32位根据你的下载版本）
  • 作用：程序编译成功后，运行exe时必须依赖这个dll。
  • 使用要点：
    1. 编译好的 .exe 程序要和 SDL2.dll 放在同一个目录下才能正常启动；
    2. 或者把dll放到系统C:\Windows\System32（不推荐，打包程序不方便）；
    3. 开发阶段，IDE运行项目也需要能找到这个dll。

include

头文件目录（.h）

  • 包含 SDL.h、SDL_types.h 等所有SDL声明头文件。
  • 作用：写代码 #include <SDL2/SDL.h> 的来源。编译器在编译阶段，从这里读取函数、结构体、宏定义。
  • 使用要点：
    • 在VS/CMake编译配置里，添加包含目录，指向这个include文件夹。
    • 只负责告诉编译器“函数长什么样”，不包含实现代码。

lib

库文件目录（静态库 .lib / 导入库 .lib）

  • Windows下SDL这里是导入库（不是完整静态库）：SDL2.lib、SDL2main.lib
  • 作用：链接阶段使用。告诉链接器，函数的实现存在 SDL2.dll 里面。
  • 使用要点：
    1. IDE配置，添加库目录指向这个lib文件夹；
    2. 链接器附加依赖项填写：SDL2.lib;SDL2main.lib；
    3. SDL2main.lib 用来接管Windows程序入口，替换main函数，SDL程序一般都要链接它。

share

资源文档文件夹

  • 里面存放许可证、readme文档、cmake配置文件、man手册等。
  • 作用：开发基本用不到，是开源项目附带的法律声明、文档、cmake支持文件。
  • 使用要点：写代码、编译链接完全不需要引用这个文件夹。CMake项目可以自动读取里面的cmake脚本方便查找SDL。

快速配置总结（VS为例）

  1. 包含目录：...\SDL\include
  2. 库目录：...\SDL\lib
  3. 链接器附加依赖：SDL2.lib;SDL2main.lib
  4. 运行：把 bin\SDL2.dll 复制到exe同目录
