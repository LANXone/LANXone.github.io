为什么短短几行C++程序会有2~3MB这么大?

核心原因

你写的短短几行C++代码，编译出来exe达到2MB，不是你的代码本身大，是编译器默认把C++标准库（运行时库）打包进exe里面了，这个叫静态链接。

1. 静态链接（默认很多IDE：Dev-C++、MinGW）

举例子：

你只写了输出一句话。
但是cout属于C++标准库，静态链接时：
✅ 编译器把整个libstdc++库里面你用到的代码，复制打包进exe
哪怕只用了一点点cout，也要带上一大段底层IO、内存管理代码。
结果：exe 1~3MB很常见。

就像：你只是想用一把螺丝刀，但是静态打包直接把整个工具箱一起塞给你。

2. 动态链接（可以让exe很小，几十KB）

动态链接：不把库打包进exe，exe运行时去调用系统里单独存在的dll文件。
缺点：换一台电脑运行，如果缺少对应的dll，程序直接打不开。
所以MinGW默认静态打包，保证拷到别的电脑可以直接运行。

3. 额外增大体积的其他因素

  1. Debug调试模式（罪魁祸首！）
    Debug版本会额外嵌入大量调试信息、符号表。同样代码，Debug版体积远大于Release发布版。
    👉 想缩小体积：切换到Release模式编译。
  2. 没有开启代码优化，保留很多无用代码。
  3. 如果你用的是64位编译器，生成的程序本身会比32位更大。

✅ 怎么缩小exe体积（MinGW/g++）

  1. 切换到Release（关闭调试符号）
  2. 编译时加优化参数：
  • -Os：体积优化
  • -s：删掉所有调试符号信息
    加完，这个cout小程序，能压缩到几百KB。

一句话区分考点（应付考试）

  • 静态链接：库代码复制进exe，文件大，可独立运行，不依赖外部dll
  • 动态链接：库放在外部dll，exe很小，依赖系统dll文件

PS: PE文件格式+CPU寻址机制限制, exe大小应当在 4GB 以下

C++游戏开发:储备知识

classes, templates, smart pointers, and the STL（C++）简单介绍

1. Classes 类

C++面向对象的核心，封装数据与操作数据的函数。

  • 把成员变量（属性）、成员函数（行为）打包成一个类型。
  • 支持访问控制：public/private/protected，实现封装；还支持继承、多态。

2. Templates 模板

泛型编程工具，让函数/类不绑定具体类型，一份代码可以适配多种数据类型。

  • 函数模板：同一个函数可以处理 int、double、string 等。
  • 类模板：最典型就是 std::vector<T>，T 就是模板参数。

3. Smart pointers 智能指针

自动管理堆内存的指针，替代裸指针，解决内存泄漏问题，本质是RAII（资源获取即初始化）。

  • std::unique_ptr：独占所有权，不能拷贝，只能移动；开销最小。
  • std::shared_ptr：共享所有权，引用计数，计数归零自动释放内存。
  • std::weak_ptr：配合 shared_ptr，解决循环引用，不增加引用计数。

核心：离开作用域时自动析构释放内存，不用手动 delete。

4. STL（Standard Template Library）标准模板库

C++标准库的泛型组件集合，全部基于模板实现，分4大块：

  1. 容器 Containers：存放数据。vector、string、map、unordered_map、set、deque、list。
  2. 迭代器 Iterators：容器的“指针”，统一遍历不同容器。
  3. 算法 Algorithms：通用函数，sort、find、for_each，通过迭代器操作容器。
  4. 函数对象 Functors：可调用对象，用于算法自定义行为。

一句话总结

  • Class：面向对象，封装；
  • Template：泛型，类型无关代码；
  • Smart pointer：安全自动内存管理；
  • STL：一套现成模板容器+算法库，日常C++开发主力。

自学规划

从零手写同步回合制游戏（不使用成品引擎）学习规划笔记

对话整理：目标游戏玩法参考《紫色晶石》《节奏地牢》，自制底层引擎（仅使用SDL/SFML等基础底层库，不使用Unity/Godot/UE）

需求概述

目标：从零开发游戏，不依赖现成游戏引擎。核心玩法为同步回合制，网格地图，类似紫色晶石（玩家行动消耗AP，玩家一轮行动结束后所有敌人统一行动）、节奏地牢（回合驱动）。想了解需要学习的内容、技术栈，以及C++内存难点、配套学习教程。

一、技术方案选型

区分概念：不使用成品引擎 ≠ 不能用底层库；底层库仅负责窗口、渲染、输入、音频；回合逻辑、战斗、AI、地图全部手写。

两条路线

路线A：C++ + 底层库（推荐，Stoneshard 使用C++）

  • 图形库：SDL2（首选，跨平台2D像素）；备选 SFML（API更友好）
  • 音频：SDL_mixer / FMOD
  • 字体渲染：SDL_ttf
  • 构建工具：CMake
  • 数据解析：nlohmann/json（读取地图、配置）
  • 地图编辑器：Tiled，导出json，自行写解析器

路线B：Rust + Macroquad / Piston

优势：内存安全，编译期规避悬垂指针、内存泄漏；适合独立开发者快速原型。缺点是生态相对C++小。

❌ 不推荐直接裸写Win32+原生OpenGL，前期大量精力消耗在图形底层，耽误回合玩法原型开发。

核心架构思想

  1. 游戏主循环：初始化 → 循环（读取输入 → 更新游戏逻辑 → 渲染画面 → 控制帧率）
  2. 同步回合状态拆分
    • WAIT_PLAYER：等待玩家输入，生成行动意图
    • PLAYER_ACT：执行玩家行动，消耗行动点AP
    • ENEMY_TURN：全部敌人依次执行AI行动
    • ANIM_PLAY：播放动作动画，暂停逻辑
  3. 逻辑与渲染严格分离：回合逻辑使用固定tick，渲染帧率不受限制，保证战斗逻辑稳定。
  4. 推荐简易ECS（实体组件系统）：实体Entity，属性Hp/Ap/Position/Buff为Component；原型阶段可以先用结构体数组，后期重构。

核心模块清单

  1. 网格Grid系统：格子坐标、世界坐标互转、可通行标记、墙壁
  2. FOV视野：Recursive Shadow Casting（紫色晶石黑暗视野）
  3. A*网格寻路：敌人寻路
  4. 行动队列 Action Queue：行动入队，回合阶段顺序执行
  5. AP行动点系统：移动、攻击、技能消耗行动点
  6. Buff/状态系统：在【回合开始】【行动前】【受伤】【回合结束】触发
  7. 伤害计算、命中判定
  8. AI逻辑：仅敌人回合执行，原型先用简单AI（靠近→可攻击则攻击）
  9. 像素渲染、精灵表、相机视口
  10. 输入解耦：输入只生成行动意图，不在输入回调直接修改游戏世界
  11. 资源加载、存档序列化

开发迭代顺序（MVP优先，禁止先做美术）

  1. 阶段1：最小引擎骨架（1~2周）
    SDL窗口，游戏循环，键盘输入，绘制方块，网格移动。目标：黑白方块地图，可以移动玩家方块。
  2. 阶段2：同步回合原型（核心MVP）
    修改为回合模式，移动消耗AP；玩家操作结束，全体敌人统一行动；实现状态机、行动队列。此时全是方块，但核心玩法跑通。
  3. 阶段3：战斗与实体系统
    血量、攻击判定，buff系统，A*敌人寻路。
  4. 阶段4：FOV视野、Tiled地图加载
    黑暗视野，解析Tiled地图json。
  5. 阶段5：动画、音效，替换方块为像素精灵
    帧动画、攻击音效，动画阻塞回合逻辑。
  6. 阶段6：UI、物品、存档、敌人种类、数值平衡
    血条、物品栏、拾取装备、存档读档。
  7. 阶段7：优化、打包发布

二、C++内存管理难点（游戏开发场景）

C++没有GC，内存生命周期完全由程序员手动控制。错误常表现为间歇性bug，Debug正常Release随机崩溃。

  1. 栈 vs 堆
    栈：局部变量，函数退出自动销毁；栈空间很小，大数组容易栈溢出。
    堆：new分配，必须手动delete；适合大量实体、地图数据。

坑：保存栈对象指针到全局队列，函数退出对象销毁 → 悬垂指针。

  1. 悬垂指针（野指针）
    指针还存在，但指向内存已经释放。访问时属于未定义行为，可能乱数据、随机崩溃。回合行动队列极易踩坑。
  2. 内存泄漏new之后忘记delete。敌人死亡不释放内存，长时间游玩内存持续上涨。程序不会报错，只会慢慢吃内存。
  3. 重复释放 double free
    一块内存delete后再次delete，破坏堆结构，随机崩溃。典型场景：ECS实体多处写删除逻辑。
  4. 浅拷贝陷阱
    默认拷贝仅复制指针，两个对象共用同一块堆内存；一个析构后另一个指针失效。角色、物品结构体高频踩坑。
    解决：手写深拷贝，或禁用拷贝。
  5. 内存所有权问题
    谁负责释放内存？行动队列保存Action指针时，如果所有权约定不清，极易出现泄漏或double free。
    现代C++方案：std::unique_ptr（单一所有权，优先推荐）；谨慎使用std::shared_ptr（循环引用会泄漏）。
  6. new[] / delete[] 必须配对
    数组分配new[]，释放必须用delete[]，混用为未定义行为。
  7. 未定义行为 UB
    内存错误没有固定报错表现：可能正常运行、随机崩溃、只在打包后出错，bug根源和崩溃位置不在一起。

✅ 降低C++内存风险的工程规范（回合引擎推荐）

  1. 优先栈对象，临时Action、小结构体尽量栈分配。
  2. 容器优先值语义：std::vector<Entity>，而不是vector<Entity*>，vector自动管理内存。ECS组件数组推荐这种写法。
  3. 堆对象优先std::unique_ptr，少用shared_ptr。
  4. 实体用ID代替裸指针（强烈推荐）
    实体使用uint64_t整数ID；维护unordered_map<uint64_t, Entity>。所有Action、buff、AI只存实体ID，访问实体通过ID查找。实体销毁直接删除map条目，直接消灭悬垂指针。

一句话总结：C++内存难不在于语法，而在于手动管理生命周期与所有权；错误行为飘忽，难以定位。

哈希表:快乐数

哈希表：快乐数

什么是快乐数？

「快乐数」定义：对于一个正整数，每一次将该数替换为它每个位置上的数字的平方和。如果这个过程结果为 1，则这个数是快乐数；如果循环中永远变不到 1，就不是快乐数。

上面用 vector + find() 查找是 O(n)，换成 unordered_set 可以把查找降到 O(1)。

核心思路：如果数字重复出现，说明陷入循环，永远到不了 1。

复杂度分析：

  • 时间复杂度：不确定上限，取决于是快乐数还是循环。但每次查找 O(1)
  • 空间复杂度：O(k)，k 为出现过的数字个数

快慢指针法（双指针，空间 O(1)）

不用哈希表也能检测循环 —— 和「判断链表有没有环」同一个思路：快指针每次走两步，慢指针每次走一步，相遇就说明有环。

总结

哈希表（hash）其实就是空间换时间，要是有强对应的话会很好用。

熟悉 vector 的各种方法事半功倍，还有 #include <algorithm> 里的各种函数（如 find()）。

快慢指针 — O(1) ⭐⭐⭐⭐⭐

unordered_set 无序集合（C++）

底层：哈希表，元素无序，不重复。

头文件：#include <unordered_set>

✅ 核心属性

  1. 元素唯一：不能存放重复的值，插入重复元素会直接忽略。
  2. 无序存储：遍历顺序不是插入顺序，也不是从小到大排序。（对比 set：红黑树，自动升序）
  3. 查找、插入、删除平均 O(1)，最坏 O(n)（哈希冲突）

set（有序集合）增删查稳定 O(logn)

⚠️ 高频坑（刷题考点）

  1. 不能用下标 st[0] 访问！没有 [] 运算符，和 vector/map 不一样。
  2. 迭代器遍历顺序不确定，不要依赖顺序。
  3. 自定义结构体不能直接放进 unordered_set，需要自己写哈希函数；普通int、string可以直接用。
  4. st.find(x) != st.end() 用来判断元素存在；st.count(x) 也可以，返回0或1。

🆚 unordered_set vs set

unordered_set set

重复元素 不允许 不允许

只需要去重 + 判断某个元素是否存在，不关心顺序 → 优先 unordered_set。
