Godot04:瓦片碰撞与 Y 轴排序（TileSet 物理层）

上一篇把地图画出来了，但角色现在能直接穿过树、石头和一切装饰物。这一篇先给瓦片加碰撞（给 TileSet 添加物理层、切到 Paint 选好属性编辑器、逐个塑造图块的碰撞箱），再用 Y 轴排序让树能挡住角色。

第一步：为 TileMap 添加物理层

物理层建在 TileSet 资源里，不是建在 TileMap 节点的 Layers 里，这是最容易走错的一步。

  1. 选中 TileMap 节点，在 Inspector 里点开 Tile Set 属性，展开这个资源。
  2. 找到 Physics Layers 分组，点 Add Element。

添加后不会立刻看到任何变化，但它是后面所有操作的前提：没有这一项，图块属性里根本不会出现画碰撞的地方，很多人卡在"找不到碰撞选项"就是漏了这一步。

同时这一项也决定了碰撞体落在哪个 2D 物理层：展开它可以看到 Collision Layer，默认 Layer 1。角色的 CharacterBody2D 碰撞掩码默认也是 Layer 1，所以保持默认就能互相检测到。以后要给敌人、子弹单独分组，再回来改这里和节点的掩码。

第二步：切到 TileSet 页签，选图块集、画笔、属性

物理层加好后，底部切到 TileSet 页签，按顺序做三件事：

  1. 先选图块集：左侧 Tile Sources 里选中要改的素材，比如 objects.png。
  2. 再选画笔：工具栏切到 Paint（不是 Setup，也不是 Select）。
  3. 最后加属性：左侧 Paint Properties 里点 Select a property editor 下拉，依次选 Physics → Physics Layer 0。

下拉里同级的还有 Rendering、Terrain、Navigation、Custom Data，物理层只是其中一项。Physics Layer 0 对应第一步里 Add Element 加出来的第一项。

选完之后，左侧就变成碰撞形状的编辑区：上面是放大的图块预览，下面是物理属性（linear_velocity、angular_velocity、polygon 0 等）。前两项是给会动的图块（比如移动平台）用的，静态地图不用管。

第三步：选中瓦片，塑造碰撞箱

在右侧 Base Tiles 网格里点一下要挡人的图块（截图里是那棵树），左侧编辑区会切到它。编辑区里有一个带四个白色控制点的矩形，用鼠标拖动这四个点，把矩形缩到真正该挡人的范围：树干和底部那一段，树冠留给角色叠上来。

改完一块再看下一块。只给实心的图块加碰撞：树、石头、墙、围栏。草地、路面、装饰这些小图块不要加，否则角色会被地面卡住。

只框住该挡的部分：碰撞箱画得越大，角色离树越远就被挡住，在俯视角游戏里会显得很硬。一般贴着树干和树根画，树冠完全放开，角色能走进树冠下面，视觉上也更自然。

大图块（比如 2×2 的树）的碰撞是在图块自己的坐标系里画的，图块占多大，坐标范围就有多大，不用管它在地图上的位置。

第四步：Y 轴排序，让树能挡住角色

碰撞管的是"能不能过去"，Y 轴排序管的是"谁盖住谁"。不打开它，角色永远画在树的上面，从树根前走过也不会被树挡住。

先开节点级的开关：

  1. 选中参与排序的节点，Inspector 顶部 CanvasItem → Ordering，勾上 Y Sort Enabled（截图里默认是 Off）。
  2. 这一层管的是"节点与节点之间"的排序：树和角色要挂在同一个也开了 Y Sort Enabled 的父节点下（比如 world），否则图块只在自己内部排序，根本不会和角色比大小。
  3. TileMap 的每个图层在 Layers 里还有独立的 Y Sort Enabled（上一篇提过），要挡住角色的那一层保持开启。

再给单个图块定"排序中心"：

  1. 底部切到 TileSet 页签，工具选 Paint。
  2. Paint Properties 下拉里选 Rendering。
  3. 展开 Y Sort Origin，把中心点拖到树根、图块底部那一行。

Y Sort Origin 是像素偏移，决定这块图块拿纵坐标上的哪一点去和角色比大小。截图里那棵树把中心放在树干底部：

  • 玩家站在中心上方（Y 更小）时，图块画在玩家前面，树把人挡住；
  • 玩家走到中心下方时，玩家画在上层，盖住树的下半截。

排序中心别随手丢在图块正中。像素角色的原点在脚底，中心太靠上会让人离树老远就被挡住，太靠下则几乎永远不会被树盖住。贴着树干和树根那一行最稳。

验证：让角色去撞一下，再绕到树后

  1. 顶部菜单 调试 → 可见碰撞形状，运行后地图上会显示碰撞多边形，画没画上、位置对不对一眼就能看出来。
  2. 按 F5 运行，走向树和石头，角色应该被挡住；贴着墙走能滑过去，这是 move_and_slide() 自带的滑动处理。
  3. 再从树的上方和下方各走一遍，看角色和树的先后顺序有没有跟着换。

角色能挡住的前提是它自己也有碰撞形状。Godot01 里加的 CollisionShape2D 在这里要顺手确认一下：Shape 不是 <empty>，并且位置对齐脚底而不是整张立绘，否则会感觉"人还离着树老远就被挡住"。

碰撞或遮挡不对，按这个顺序排查

现象 最可能的原因
图块属性里完全没有 Physics 项 TileSet 的 Physics Layers 没加元素
有碰撞矩形，但角色照穿 TileMap 的 Layers 里这一层没勾 Collision Enabled
只有部分图块挡人 只给选中的图块画了碰撞，同类的其他图块没画
角色被地面卡住、走不动 地面、草地这些图块也加了碰撞
角色离障碍物老远就被挡住 碰撞矩形画得比图块大，或者角色的 CollisionShape2D 偏移了
撞上去抖动、被弹开 相邻图块的碰撞矩形互相重叠
角色永远盖在树上面 节点没开 Y Sort Enabled，或角色和 tilemap 不在同一个开了排序的父节点下
角色永远被树盖住 图块的 Y Sort Origin 设得太靠上，排序点高过了角色脚底
只在图块之间排序，角色不参与 TileMap 图层的 Y Sort Enabled 和父节点的开关只开了一个

三个"层"别搞混

名字 在哪 管什么
Physics Layers（TileSet） TileSet 资源 Inspector 允许图块有碰撞，决定碰撞体归哪个 2D 物理层
Collision Enabled（图层的） TileMap 的 Layers / TileMapLayer 节点 这一层画的图块要不要真的生成碰撞体
Collision Layer / Mask（节点的） 各节点自己的 Collision 分组 谁和谁互相检测

前两个管"图块有没有碰撞"，第三个管"碰撞和谁发生关系"。改完没反应，九成是前两个之一漏了。

如果用的是 TileMapLayer

TileMapLayer 流程完全一样：物理层还是建在 TileSet 资源里，碰撞箱还是用 Paint 加 Physics Layer 0 来画，Y Sort Origin 也还是在 Paint Properties → Rendering 里拖。区别只在开关位置——原来 TileMap 里 Layers 数组的 Collision Enabled 和 Y Sort Enabled，现在变成 TileMapLayer 节点自己 Inspector 上的同名属性。

Godot03:制作瓦片地图（TileMap 与 TileSet）

前两篇已经让角色能站在场景里跑动，但脚下还是空的。这一篇给 world 节点铺上瓦片地图：先建 TileSet 资源，把素材图注册成图块，再手动划出真正要用的图块。

关于 TileMap 的弃用：Godot 4.3 起 TileMap 节点被标记为 Deprecated，官方推荐改用 TileMapLayer（一个图层一个节点）。本文按课程仍用 TileMap，因为 TileSet、图块、碰撞这些核心概念完全一致；文末附两种写法的对照表，以后新项目可以直接换。

第一步：给 world 添加 TileMap 节点

和上一篇给角色加 AnimatedSprite2D 的方法一样，先选中场景里的 world 节点，让它成为父节点。

  1. 点击场景面板左上角的 + 添加节点。
  2. 在搜索框输入 tile。
  3. 选中 TileMap，点击 Create。

注意搜索结果的预览里有一条红色提示：TileMap 已经 Deprecated。它仍然可以用，只是不再增加新功能，所以按课程继续往下走没问题。

第二步：新建 TileSet 资源

选中刚创建的 TileMap，在右侧 Inspector 里找到 Tile Set 属性，此时是 <empty>。

  1. 点击 <empty> 右侧的下拉按钮。
  2. 在 New 分组里选择 TileSet。

下拉里另外两项是 Quick Load... 和 Load...，用来复用已经存成 .tres 的瓦片集。同一个项目里做多张地图时，直接 Load 同一份 TileSet，图块和碰撞就不用重做一遍。

TileSet 是一个资源，不是节点。它保存"有哪些图块、每个图块怎么切、带什么碰撞和地形"；TileMap 节点只负责"用这套 TileSet 在场景里画"。两者分开，才能做到一张图块表被多张地图共用。

建好后顺手看一眼 Inspector 里 TileSet 的 Tile Size（默认 16×16）。素材的单格不是 16×16 时必须先改成实际尺寸，否则画布上的网格和图案对不上，整张地图都会错位。想让别的场景也复用这张图块表，可以用资源下拉里的 Save As... 把它存成 .tres，之后再用 Load... 加载。

第三步：把瓦片素材拖进 Tile Sources

新建好 TileSet 后，底部面板多出一个 TileSet 页签（和 TileMap 页签并排，别点错）。

  1. 切到底部 TileSet 面板。
  2. 左侧选中 Tile Sources。
  3. 从 FileSystem（资源管理器）里把需要用的 png 直接拖进来。

每拖入一张 png，就会多一个 Atlas 图源，Godot 自动给它分配一个 ID（截图里分别是 0、1、2）。图源左侧的缩略图就是这个 png 的预览。

第四步：用橡皮擦清掉默认切分

拖进来之后，Godot 会按 Texture Region（截图里是 16×16）把整张图自动切成格子，并把所有格子都登记成图块。问题是：

  • 素材图里通常有一大片空白、装饰线、水印，这些也会被切成图块；
  • 真正要用的图块可能不是 16×16，比如一棵树是 2×2 格。

所以先把自动切分全部清掉，改成自己划。

  1. 在 TileSet 面板的工具栏里选中橡皮擦（Setup、Select、Paint 右边那个橡皮图标）。
  2. 在右侧网格上按住左键划过去，把默认的图块全部擦掉。

擦完之后网格还在，只是格子不再是"图块"。这一步的意义是：图块不是切开就有的，而是由你主动登记出来的，登记时才决定它占多大、带什么属性。

第五步：手动划出需要的图块

还是 Setup 模式，在右侧的图片网格上按需要创建图块：

  • 单击一个格子 → 创建一个 1×1 的小图块；
  • 按住 Ctrl 连续点击 → 一次登记多个小图块；
  • 按住 Shift 拖拽框选 → 把框住的若干格合并成一个大图块，比如 2×2 的树、3×2 的石头。

截图里 ID 2 对应 objects.png：左上角那些 1×1 的杂物是小图块，中间那棵树框住了 2×2 的范围，就是一个大图块。

大图块虽然占多格，但在 TileMap 里仍然是一个整体：选一次、画一次就摆好一棵树，不用拼四块，碰撞也能按整棵树的形状设置。

Setup 不是作画的地方。 底部 TileSet 和 TileMap 是两个页签，Setup 只存在于 TileSet 页签里：右侧网格是选图块的地方，左侧 Atlas 参数（ID、Texture Region 等）是选中图块后调属性的地方。要真正把图块画进场景，必须切到 TileMap 页签，在 Setup 里怎么点都不会往地图上放东西。

第六步：选图块，把地图画出来

图块划好了，把底部切到 TileMap 页签，开始铺地图。

  1. 切到底部 TileMap 面板，左侧选中 objects.png 这个图源。
  2. 点工具栏最左边的选择工具，在右侧图块列表里点选要用的图案；按住 Shift 可以多选。
  3. 换成画笔（铅笔图标），回到画布按住左键拖动，图块就画上去了。
  4. 画错了用右键擦除（右键就是临时橡皮擦，不用先切工具），或者 Ctrl+Z 撤销。

截图里那四棵树是同一个 2×2 大图块画了四次。大图块落笔时以鼠标所在的格子为左上角，画一次就摆好整棵，不用拼四块。

画布上的橙色网格就是格子边界，右侧那两个网格图标分别控制网格显示和当前图块高亮，对不准位置时可以打开看一眼。

工具栏其余几个也常用：

工具 作用
直线 / 矩形 拖一条线或一个矩形，一次铺一排、一片图块，铺地面很快
吸管 点画布上已有的图块，把它变成当前选中的图块
旋转 / 镜像 落笔前调整图块朝向，同一张素材能复用出更多变化
Layer0 下拉 切换当前画在哪一层（层是在 TileSet 的 Layers 里定义的）

按住 Shift 多选图块还有个用处：配合随机化（randomization），落笔会在选中的几个图块里随机挑一个。铺草地、碎石这类要自然散开的地面时，选三五种变体一起画，比手动一个个摆快得多。

图层：重命名、新建，还有 Y Sort

画完会发现地面和树混在同一个 Layer0 里，想单独藏起树来调地面就做不到。图层在 Inspector 里管理——选中 TileMap，最下面的 Layers 就是图层列表。

  1. 重命名：点 Name 那一列，把 Layer0 改成看得懂的名字，比如 ground、objects。底部 TileMap 面板的层下拉会同步更新。
  2. 新建图层：点最下面的 + Add Element 追加一层。建议地面一层、树和石头一层，方便分别隐藏、分别设碰撞。
  3. Enabled：取消勾选可以临时隐藏这一层，对着地形摆装饰时很好用。
  4. Y Sort Enabled：打开后这一层里的图块按 Y 坐标排序，站在树后面时树的下半部分会盖住角色的一部分，走到树前面角色又能盖住树。Y Sort Origin 是排序基准点，大图块（比如 2×2 的树）排序位置不对时调它。

图层顺序就是绘制顺序：列表越靠下越晚画、越靠上。所以地面放第一层，树、房子这类要挡住角色的放后面；角色能不能被树挡住，还要配合父节点的 Y 排序，这里先留个印象。

三个概念别搞混

名词 是什么 在哪看
Tile Source（Atlas） 一张 png 素材在图集里的注册，带自己的 ID TileSet 面板左侧列表
Tile（图块） 从图源里划出的一个矩形区域，可带碰撞、地形、偏移 Setup 模式在网格上划出来
TileSet 以上所有图块的集合，是一个资源文件 Inspector 的 Tile Set 属性

画地图时选中的就是某个 Tile Source 下的某个 Tile（按 ID 定位），所以图块一旦划错位置，地图上已经画好的部分也会跟着错位。

附：以后新项目改用 TileMapLayer

Godot 4.3 之后 TileMap 被 TileMapLayer 取代，核心区别只有一个：一个图层就是一个节点。以前所有层都在同一个 TileMap 里、只能在 Inspector 的 Layers 里改；现在每层单独一个节点，可见性、modulate、碰撞层、Y 排序都能分开设，用时把节点摆好就行。

操作对照：

要做的事 TileMap（本文写法） TileMapLayer（新写法）
建节点 一个 TileMap，所有层塞在里面 每层一个 TileMapLayer 节点
切换当前层 底部 TileMap 面板的 Layer0 下拉 直接在场景面板里选中对应节点
设置图块表 Inspector → Tile Set 同样 Inspector → Tile Set
划图块 底部 TileSet → Setup 完全相同
画地图 底部 TileMap → 画笔 完全相同

如果手上是旧项目，可以一键转换：选中 TileMap 节点，打开底部 TileMap 面板，点右上角的工具箱图标，选 Extract TileMap layers as individual TileMapLayer nodes，原来的每层都会变成单独的 TileMapLayer 节点。

三行代码换个位置，就是三种遍历

既然「前中后」只取决于那三行的顺序，那么把 push_back 挪一下，同一个函数骨架就能变成另外两种遍历：

遍历 三行的顺序 访问中间节点的时机
前序 中 → 左 → 右 一进来就访问
中序 左 → 中 → 右 左边全部处理完才访问
后序 左 → 右 → 中 两个孩子都处理完才访问

三个函数除了那一行的位置，一个字都没变。所以不要去背「前序是中左右」这种口诀，要背的是「访问动作插在哪两个递归调用之间」——前者是结论，后者是原因，记住原因就不会记混。

顺带说一个判断方法：如果一道题让你输出序列，先问自己「我是在进入节点时就知道答案了，还是要等孩子都告诉我答案之后才知道？」前者前序，后者后序。至于中序，它几乎是二叉搜索树的专属——因为中序遍历出来的就是升序序列。

手工跑一遍，看清递归的过程

递归之所以难，是因为它在纸面上是「静态」的，但实际执行是「动态」的。拿这棵树跑一遍前序：

步骤 当前调用 发生了什么 res
1 tar(1) 访问 1，然后往左 [1]
2 tar(1) → tar(2) 访问 2，然后往左 [1,2]
3 tar(1) → tar(2) → tar(4) 访问 4，然后往左 [1,2,4]
4 tar(4) 的左孩子 是 nullptr，立即 return [1,2,4]
5 tar(4) 的右孩子 是 nullptr，立即 return [1,2,4]
6 tar(4) 结束，回到 tar(2) 的右孩子 调用 tar(5)，访问 5 [1,2,4,5]
7 tar(5) 的左右孩子 两次 return，tar(5) 结束 [1,2,4,5]
8 tar(2) 结束，回到 tar(1) 的右孩子 调用 tar(3)，访问 3 [1,2,4,5,3]
9 tar(3) 的左右孩子 两次 return，全部结束 [1,2,4,5,3]

从这张表能读出三件事：

  1. 执行路线是一条「一路向左钻到底，撞到空才回头」的折线，不是按层走的，也不是按序列顺序走的。这就是「深度优先」四个字的字面意思。
  2. res 里元素的先后顺序，等于每个节点被访问的那一瞬间的先后顺序。前序把访问放在函数第一行，所以「第一次到达节点」就记下来；后序放在最后一行，所以是「离开节点」才记下来。
  3. 那些 return 不是可有可无的兜底，它们是递归能停下、能回头的唯一机制。去掉 if (cur == nullptr) return; 这行，程序会在 nullptr 上继续取 ->left，直接段错误。

一个容易忽略的细节：vector<int>&

上面代码里 res 前面那个 & 不是可有可无的装饰。如果写成 void tar(TreeNode* cur, vector<int> res)（不带 &）：

  • 每次递归调用都会复制一份 vector 传给下一层；
  • 子层往自己的副本里 push_back，父层完全看不到；
  • 结果就是只有最外层那一层真的写进了东西，返回的序列几乎是空的；
  • 而且每层复制一次，总拷贝量是 O(n2)O(n^2)O(n​2​​)，数据量大时直接超时。

这是初学递归最容易踩的「玄学 bug」：代码看着对，结果不对，还找不到错在哪。症状是「结果缺元素或者只有几个」，第一反应就去看参数是不是该传引用。

另一种写法是让递归函数直接返回 vector<int>：

这种写法逻辑更「纯」，但每一层都在新建和拼接 vector，复杂度退化成 O(n2)O(n^2)O(n​2​​)（或者需要额外的移动语义优化）。所以遍历类的题一律用「引用参数收集结果」的写法，这也是 LeetCode 上一贯的风格。

关于递归

从最简单的二叉树遍历就能看出来二叉树的使用和递归息息相关，因为二叉树不像先前的数组、栈和队列是一维的数据结构，没法简单得顺序遍历。

这句话值得再往前推一步，因为它才是理解递归的入口。

为什么顺序遍历在树上失效了

链表只有一个 next：「下一个是谁」永远是确定的，所以一个 while 循环就能走完。二叉树的每个节点却有两个孩子，走到左子树的叶子之后，要回到父节点才能去右子树——可你手里只有一个 TreeNode* cur，它没有 parent 指针，回不去。

于是问题变成：我要记住来时的路。

  • 用系统帮你维护的栈来记 → 这就是递归；
  • 用自己开的 stack 来记 → 这就是迭代；
  • 用叶子节点的空指针硬存「回程票」→ 这就是 Morris 遍历。

三种做法的本质是同一件事：在一维的、只能往下走的指针世界里，强行保存一棵二维的树的行走路径。 递归之所以看起来「自然」，只是因为这个栈由编译器帮你管了，你看不见它。

树是「用自己定义自己」的结构

回想二叉树的定义：

二叉树是空树，或者由一个根节点加上两棵二叉树（左子树和右子树）组成。

这段话本身就是一个递归。结构的定义是递归的，那么处理它的代码也是递归的——这不是巧合，而是最省力的选择。

打个比方：递归解决问题的思路不是「把大问题切成小问题」，而是「把问题换成同一个问题，只是规模小一号」。你不需要知道怎么遍历一棵有 100 万个节点的树，你只需要知道：

  • 怎么访问当前这个节点；
  • 剩下的，交给「遍历左子树」和「遍历右子树」去做——并假设它们一定是对的。

这种「假设子问题已经解决」的信任，就是数学归纳法。写不出递归的人，通常不是不会写代码，而是不敢信任这一步。

递归三要素（拿刚才的代码对号入座）

任何一道树题，写之前先回答三个问题，缺一个就写不出来：

要素 问题 对应到遍历代码
参数与返回值 我需要什么信息？我要把什么信息带出去？ TreeNode* cur 是「当前处理谁」，vector<int>& res 是「结果往哪放」
终止条件 什么时候可以直接返回？ cur == nullptr
单层逻辑 当前这一层，我具体做什么？ 访问 cur，然后递归左右

很多人卡在第一步：参数到底要不要带 res？要不要返回值？判断标准很简单——信息是往下传，还是往上传？

  • 往下传（比如「当前路径和」「当前深度」）→ 加参数，前序用得多。
  • 往上传（比如「这棵子树的高度」「这棵子树是否平衡」）→ 用返回值，后序用得多。

终止条件为什么是「空节点」而不是「叶子节点」

新手常写：

这个写法的问题在于：叶子节点自己被漏掉了。你在递归之前就得先把叶子访问掉，于是每个分支都要单独处理「孩子是不是叶子」，代码会迅速膨胀成一堆特判。

而写成 cur == nullptr，等于是把判断推到了「下一层」：

  • 叶子节点正常进入函数、正常被访问；
  • 它的两个孩子是 nullptr，各自进入函数后立刻返回。

这样所有节点走的是同一条代码路径，没有特判。这是递归写法的一个通用美学：把终止条件设在「越过边界之后」，而不是「站在边界上」。数组题里 if (l > r) return; 是同一个道理，递归到区间为空才停，而不是在区间只有一个元素时特判。

递归的两个时刻：进入与回溯

这是我认为最有价值的一条：同一个递归函数，在「进入」和「回溯」两个时刻各能做一次事。

时刻 信息流方向 适合干的事
① 进入 自顶向下（父 → 子） 传参、打印、记录路径、判断当前深度
② 中间 左子树已完成 利用 BST 有序性、找第 k 小
③ 离开 自底向上（子 → 父） 汇总子树结果、求高度、判断平衡、删除节点

所以「选哪种遍历」不是一个记忆题，而是一个信息流方向的问题：

父节点决定子节点 → 前序；子树结果汇总给父节点 → 后序；靠左右有序性 → 中序。

理解递归最直接的方法，是手动把系统栈拆出来。写一遍迭代版，你就再也不会觉得递归是黑魔法了。

更进一步：Morris 遍历（不用栈、不递归）

第四种遍历：层序（BFS + 队列）

前中后序都是深度优先，走的是一条道走到黑。还有一种完全不同的走法——一层一层来，这叫层序遍历，用的容器是队列：

int size = q.size(); 这一行是全场重点。不先记下来，while 里一边出队一边入队，q.size() 会不断变大，下一层的节点就会混进当前层，输出直接错位。这个坑几乎每个人都踩过一次。

层序的价值在于「按层」这个语义本身：

  • 求最小深度（碰到第一个叶子就停，比 DFS 快）；
  • 按层打印 / 锯齿形遍历 / 右视图；
  • 判断完全二叉树（层序里出现的第一个 nullptr 之后不该再有节点）。

复杂度：为什么树题几乎都是 O(n)

  • 时间：每个节点被进入一次、访问一次，所以是 O(n)O(n)O(n)。哪怕代码里嵌套了两个递归调用，总的调用次数也只是 2n+12n+12n+1 级别，不要因为「调用看起来很吓人」就以为是指数级。
  • 空间：递归栈的深度等于树高 hhh。平衡树 h=O(logn)h = O(\log n)h=O(logn)，退化成链的树 h=O(n)h = O(n)h=O(n)。

这里有个实际的坑：如果一个「树」实际上是 10 万个节点的单链（某些测试用例专门这么构造），递归会栈溢出。 表现为程序直接崩溃（stack overflow / 段错误），不是答案错误，很难和逻辑错误区分开。所以当你看到「递归写法过不了，但思路是对的」，先怀疑深度，换迭代。

这也解释了为什么工程代码里遍历一棵很深的树，往往用迭代而不是递归——不是不喜欢递归，是怕栈。

从「会遍历」到「会解题」

到这里，遍历本身已经没什么难的了。但真实的题目不会问你「输出前序序列」，而是会问「这棵树的深度是多少」「翻转它」「路径和等于目标值的路径有几条」。

好消息是：这些题和遍历用的是同一副骨架，差别只在「单层逻辑」那一行填什么。

遍历是骨架，题目是血肉。骨架永远是「终止条件 + 递归左右」，血肉是中间那几行。

递归的心法

最后几条，是写完上面这些之后我自己总结的：

  1. 不要试图在脑子里展开整棵树。 人脑能同时记住的层级大概就 5～7 层，而递归的展开是二维的。你越用力去「模拟」，越容易乱。真正该做的是验证「当前这一层」是否正确。
  2. 相信子问题已经解决。 写 maxDepth(root->left) 的时候，就当它一定返回了左子树的正确深度。这不是偷懒，这是递归的定义。
  3. 先用最小的例子验证单层逻辑。 一个节点的树、两个节点的树、只有左孩子的树——这三棵树能把 90% 的边界错误暴露出来。
  4. 递归写不出来时，回到三要素。 参数够不够？终止条件是什么？这一层要做什么？绝大多数「写不出来」都是因为这三条里有一条没想清楚，而不是因为不会递归。
  5. 「一看就会，一写就废」是正常的。 递归是一种需要手感的技能，看懂的瞬间和写对的瞬间之间隔着几十道题。这也是为什么我在二叉树基础知识总结那篇里给自己的最后一句提醒是「回到具体题目上手写」。

小结：前中后序只是「同一副骨架里，访问动作插在不同位置」；树和递归之所以绑定，是因为树的定义本身就是递归的，而递归的栈正好替我们保存了「二维结构在一维指针世界里丢失的来路」。想明白这两句话，二叉树的题目就从「背模板」变成了「填骨架」。

一、四种树

解题中最常打交道的是前两种（没有数值要求），理解后两种（有数值、有序）。

种类 定义要点 关键结论
满二叉树 只有度为 0 和度为 2 的结点，叶子全部在同一层 深度 k ⇒ 共 2^k − 1 个节点
完全二叉树 除最底层外每层填满，最底层节点自左向右连续集中在最左 底层为第 h 层 ⇒ 该层有 1 ~ 2^(h−1) 个节点
二叉搜索树 左子树全部 < 根 < 右子树全部，且左右子树也是 BST 中序遍历 = 单调递增
平衡二叉搜索树 空树，或左右子树高度差绝对值 ≤ 1，且左右子树也各自平衡 增删查稳定 O(log n)

完全二叉树的典型陷阱

易错 1：只要出现「左边空、右边有」的错位，或某层没填满却已进入下一层，就不是完全二叉树。判定标准只有一条：自左向右连续填满。

易错 2：堆（优先级队列）是一种完全二叉树，只是额外保证了父子节点的大小顺序；所以堆既不是满二叉树，也不一定是 BST。

容器底层要知道：map / set / multimap / multiset 底层是平衡二叉搜索树（红黑树），增删查 O(log n)；而 unordered_map / unordered_set 底层是哈希表，平均 O(1)。分析复杂度时不能混。

链式存储用指针把散落各处的节点串起来（主流、好理解）；顺序存储用数组，元素在内存中连续分布。

中序 4 2 5 1 6 3 7 左 → 根 → 右（BST 上就是升序）
后序 4 5 2 6 7 3 1 最后才是根（适合自底向上收集信息）
层序 1 2 3 4 5 6 7 逐层从左到右

易错 3：DFS 用栈（递归本身就是系统栈），BFS 必须用队列。选错容器，遍历逻辑不可能对。

遍历方式怎么选

需求 选
父节点决定子节点（自上而下传参） 前序
子树结果汇总成父节点（自下而上返值） 后序
利用 BST 的有序性 中序
按层处理 / 求最浅深度 层序

五、易错点汇总

# 易错点 正确认知
1 完全二叉树判定 必须自左向右连续填满，左空右有即错
2 堆的性质 堆 = 完全二叉树 + 父子顺序，不是「满二叉树」
3 容器底层 map/set = 平衡 BST；unordered_* = 哈希表
4 DFS/BFS 容器 DFS 配栈（递归），BFS 配队列
5 前中后序混淆 只看中间节点排第几
6 数组下标 2i+1 / 2i+2（0 起）；若从 1 开始编号则是 2i / 2i+1

六、考前 60 秒自查

  • [ ] 满二叉树节点数公式是 2^k − 1，能立刻画出深度 3 的满二叉树
  • [ ] 能一眼判断「这不是完全二叉树」：最底层没有自左向右连续填满
  • [ ] 说得出堆 = 完全二叉树、map/set 底层 = 平衡 BST
  • [ ] 数组存储：父 i → 左 2i+1、右 2i+2
  • [ ] 前中后序 = 中间节点在序列中的位置；DFS 配栈，BFS 配队列
  • [ ] 默写节点结构体：一个值 + 两个指针 + 构造函数
  • [ ] BST 的中序遍历是升序，平衡 BST 的增删查是 O(log n)

最后提醒：二叉树题的难点不在概念，而在递归——「一看就会，一写就废」。复习完基础，务必回到具体题目上手写递归三要素：参数与返回值、终止条件、单层逻辑。

Godot02:角色移动脚本（GDScript 语法复习）

上一篇 Godot01：创建一个能动的角色 搭好了节点和动画，这一篇把 player.gd 按注释逐段拆开，方便以后快速复习 GDScript 的写法和这段移动逻辑。

完整代码

语法速记

  • extends CharacterBody2D：继承节点类型，作用类似 Unity 里的 Rigidbody2D，继承后才有 move_and_slide()；可以类比 C++ 的 #include "CharacterBody2D.h"。
  • GDScript 像 Python：继承用 extends，函数用 func，变量用 var，常量用 const，类型标注写成 变量名:类型名。
  • $AnimatedSprite2D：获取当前节点下的子节点，等价于 get_node("AnimatedSprite2D")。
  • _ 开头的函数是 Godot 的内置回调：_ready() 对应 Unity 的 Start()，_physics_process(delta) 对应 Update()，delta 是上一帧到这一帧的时间间隔。
  • pass 是占位符，表示函数暂时不实现任何功能。

逻辑说明

常量与状态

SPEED 是移动速度常量；current_direction 记录当前朝向，初始为 "none"，供动画播放时判断用哪个方向的动画。

_ready()：初始动画

节点准备就绪时先播放正面待机动画。

player_movement(delta)：读取输入并设置速度

用 Input.is_action_pressed("ui_right") 这类方法判断输入动作是否按下，ui_right 等是 Godot 默认的输入动作，可以在项目设置里改。

  • 方向判断用 if / elif 链，所以同时按多个键时只有一个方向生效，优先级是：右 → 左 → 下 → 上。
  • 有输入时把 velocity 对应轴设为 ±SPEED，另一轴清零；没有输入时两轴都清零，并播放待机动画（play_animation(0)）。
  • velocity 是 CharacterBody2D 的属性，表示角色速度。
  • 最后统一调用 move_and_slide()，让角色按速度移动并处理碰撞。

play_animation(movement)：按朝向和状态选动画

参数 movement 表示状态：1 是移动，0 是静止。anim.flip_h 控制水平翻转，因为左右共用同一套动画。

朝向 移动 静止
right side_walk（flip_h = false） side_idle
left side_walk（flip_h = true） side_idle
down front_walk front_idle
up back_walk back_idle
none — back_idle

anim.play() 的参数就是动画名称，要和 SpriteFrames 里的命名一致。
