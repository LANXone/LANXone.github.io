顺带说一个判断方法：如果一道题让你输出序列，先问自己「我是在进入节点时就知道答案了，还是要等孩子都告诉我答案之后才知道？」前者前序，后者后序。至于中序，它几乎是二叉搜索树的专属——因为中序遍历出来的就是升序序列。

手工跑一遍，看清递归的过程

递归之所以难，是因为它在纸面上是「静态」的，但实际执行是「动态」的。拿这棵树跑一遍前序：

步骤 当前调用 发生了什么 res
1 tar(1) 访问 1，然后往左 [1]
2 tar(1) → tar(2) 访问 2，然后往左 [1,2]
3 tar(1) → tar(2) → tar(4) 访问 4，然后往左 [1,2,4]
4 tar(4) 的左孩子 是 nullptr，立即 return [1,2,4]
5 tar(4) 的右孩子 是 nullptr，立即 return [1,2,4]
6 tar(4) 结束，回到 tar(2) 的右孩子 调用 tar(5)，访问 5 [1,2,4,5]
7 tar(5) 的左右孩子 两次 return，tar(5) 结束 [1,2,4,5]
8 tar(2) 结束，回到 tar(1) 的右孩子 调用 tar(3)，访问 3 [1,2,4,5,3]
9 tar(3) 的左右孩子 两次 return，全部结束 [1,2,4,5,3]

从这张表能读出三件事：

  1. 执行路线是一条「一路向左钻到底，撞到空才回头」的折线，不是按层走的，也不是按序列顺序走的。这就是「深度优先」四个字的字面意思。
  2. res 里元素的先后顺序，等于每个节点被访问的那一瞬间的先后顺序。前序把访问放在函数第一行，所以「第一次到达节点」就记下来；后序放在最后一行，所以是「离开节点」才记下来。
  3. 那些 return 不是可有可无的兜底，它们是递归能停下、能回头的唯一机制。去掉 if (cur == nullptr) return; 这行，程序会在 nullptr 上继续取 ->left，直接段错误。

一个容易忽略的细节：vector<int>&

上面代码里 res 前面那个 & 不是可有可无的装饰。如果写成 void tar(TreeNode* cur, vector<int> res)（不带 &）：

  • 每次递归调用都会复制一份 vector 传给下一层；
  • 子层往自己的副本里 push_back，父层完全看不到；
  • 结果就是只有最外层那一层真的写进了东西，返回的序列几乎是空的；
  • 而且每层复制一次，总拷贝量是 O(n2)O(n^2)O(n​2​​)，数据量大时直接超时。

这是初学递归最容易踩的「玄学 bug」：代码看着对，结果不对，还找不到错在哪。症状是「结果缺元素或者只有几个」，第一反应就去看参数是不是该传引用。

另一种写法是让递归函数直接返回 vector<int>：

这种写法逻辑更「纯」，但每一层都在新建和拼接 vector，复杂度退化成 O(n2)O(n^2)O(n​2​​)（或者需要额外的移动语义优化）。所以遍历类的题一律用「引用参数收集结果」的写法，这也是 LeetCode 上一贯的风格。

关于递归

从最简单的二叉树遍历就能看出来二叉树的使用和递归息息相关，因为二叉树不像先前的数组、栈和队列是一维的数据结构，没法简单得顺序遍历。

这句话值得再往前推一步，因为它才是理解递归的入口。

为什么顺序遍历在树上失效了

链表只有一个 next：「下一个是谁」永远是确定的，所以一个 while 循环就能走完。二叉树的每个节点却有两个孩子，走到左子树的叶子之后，要回到父节点才能去右子树——可你手里只有一个 TreeNode* cur，它没有 parent 指针，回不去。

于是问题变成：我要记住来时的路。

  • 用系统帮你维护的栈来记 → 这就是递归；
  • 用自己开的 stack 来记 → 这就是迭代；
  • 用叶子节点的空指针硬存「回程票」→ 这就是 Morris 遍历。

三种做法的本质是同一件事：在一维的、只能往下走的指针世界里，强行保存一棵二维的树的行走路径。 递归之所以看起来「自然」，只是因为这个栈由编译器帮你管了，你看不见它。

树是「用自己定义自己」的结构

回想二叉树的定义：

二叉树是空树，或者由一个根节点加上两棵二叉树（左子树和右子树）组成。

这段话本身就是一个递归。结构的定义是递归的，那么处理它的代码也是递归的——这不是巧合，而是最省力的选择。

打个比方：递归解决问题的思路不是「把大问题切成小问题」，而是「把问题换成同一个问题，只是规模小一号」。你不需要知道怎么遍历一棵有 100 万个节点的树，你只需要知道：

  • 怎么访问当前这个节点；
  • 剩下的，交给「遍历左子树」和「遍历右子树」去做——并假设它们一定是对的。

这种「假设子问题已经解决」的信任，就是数学归纳法。写不出递归的人，通常不是不会写代码，而是不敢信任这一步。

递归三要素（拿刚才的代码对号入座）

任何一道树题，写之前先回答三个问题，缺一个就写不出来：

要素 问题 对应到遍历代码
参数与返回值 我需要什么信息？我要把什么信息带出去？ TreeNode* cur 是「当前处理谁」，vector<int>& res 是「结果往哪放」
终止条件 什么时候可以直接返回？ cur == nullptr
单层逻辑 当前这一层，我具体做什么？ 访问 cur，然后递归左右

很多人卡在第一步：参数到底要不要带 res？要不要返回值？判断标准很简单——信息是往下传，还是往上传？

  • 往下传（比如「当前路径和」「当前深度」）→ 加参数，前序用得多。
  • 往上传（比如「这棵子树的高度」「这棵子树是否平衡」）→ 用返回值，后序用得多。

终止条件为什么是「空节点」而不是「叶子节点」

新手常写：

这个写法的问题在于：叶子节点自己被漏掉了。你在递归之前就得先把叶子访问掉，于是每个分支都要单独处理「孩子是不是叶子」，代码会迅速膨胀成一堆特判。

而写成 cur == nullptr，等于是把判断推到了「下一层」：

  • 叶子节点正常进入函数、正常被访问；
  • 它的两个孩子是 nullptr，各自进入函数后立刻返回。

这样所有节点走的是同一条代码路径，没有特判。这是递归写法的一个通用美学：把终止条件设在「越过边界之后」，而不是「站在边界上」。数组题里 if (l > r) return; 是同一个道理，递归到区间为空才停，而不是在区间只有一个元素时特判。

递归的两个时刻：进入与回溯

这是我认为最有价值的一条：同一个递归函数，在「进入」和「回溯」两个时刻各能做一次事。

时刻 信息流方向 适合干的事
① 进入 自顶向下（父 → 子） 传参、打印、记录路径、判断当前深度
② 中间 左子树已完成 利用 BST 有序性、找第 k 小
③ 离开 自底向上（子 → 父） 汇总子树结果、求高度、判断平衡、删除节点

所以「选哪种遍历」不是一个记忆题，而是一个信息流方向的问题：

父节点决定子节点 → 前序；子树结果汇总给父节点 → 后序；靠左右有序性 → 中序。

把递归拆开：用自己开的栈写一遍

理解递归最直接的方法，是手动把系统栈拆出来。写一遍迭代版，你就再也不会觉得递归是黑魔法了。

前序的迭代版

注意压栈顺序是先右后左。因为栈是后进先出，后压进去的左孩子会先出来——这样出栈顺序才是「中左右」。压反了得到的就是「中右左」，正好是镜像。

更进一步：Morris 遍历（不用栈、不递归）

既然递归和迭代都只是在维护「来时的路」，那能不能把这条路直接存在树里？可以——用叶子节点那些空着的右指针当「回程票」临时指回祖先，用完再拆掉。这样空间复杂度压到 O(1)O(1)O(1)：

Morris 会修改树的结构（虽然事后会还原），多线程环境下不安全，实际工程里几乎不用，但它能让你彻底明白：O(h) 的栈空间到底在存什么。 知道了这一点，递归就从一个「玄学」变成了一个「实现细节」。

第四种遍历：层序（BFS + 队列）

前中后序都是深度优先，走的是一条道走到黑。还有一种完全不同的走法——一层一层来，这叫层序遍历，用的容器是队列：

int size = q.size(); 这一行是全场重点。不先记下来，while 里一边出队一边入队，q.size() 会不断变大，下一层的节点就会混进当前层，输出直接错位。这个坑几乎每个人都踩过一次。

层序的价值在于「按层」这个语义本身：

  • 求最小深度（碰到第一个叶子就停，比 DFS 快）；
  • 按层打印 / 锯齿形遍历 / 右视图；
  • 判断完全二叉树（层序里出现的第一个 nullptr 之后不该再有节点）。

复杂度：为什么树题几乎都是 O(n)

  • 时间：每个节点被进入一次、访问一次，所以是 O(n)O(n)O(n)。哪怕代码里嵌套了两个递归调用，总的调用次数也只是 2n+12n+12n+1 级别，不要因为「调用看起来很吓人」就以为是指数级。
  • 空间：递归栈的深度等于树高 hhh。平衡树 h=O(logn)h = O(\log n)h=O(logn)，退化成链的树 h=O(n)h = O(n)h=O(n)。

这里有个实际的坑：如果一个「树」实际上是 10 万个节点的单链（某些测试用例专门这么构造），递归会栈溢出。 表现为程序直接崩溃（stack overflow / 段错误），不是答案错误，很难和逻辑错误区分开。所以当你看到「递归写法过不了，但思路是对的」，先怀疑深度，换迭代。

这也解释了为什么工程代码里遍历一棵很深的树，往往用迭代而不是递归——不是不喜欢递归，是怕栈。

踩坑清单

# 坑 正确做法
1 参数忘了写 &，结果缺元素 收集结果的容器一律传引用
2 终止条件判叶子，叶子自己被漏掉 判 nullptr，让判断发生在「越过边界后」
3 前序迭代压栈顺序写反 先压右再压左，出栈才是「中左右」
4 层序不记录 size 每层开头 int size = q.size()
5 中序迭代照抄前序 必须先沿左链压栈到底
6 root 可能是空树，忘了判 函数第一行判 root == nullptr
7 递归里对同一个子树调用两次 树天然不重复，重复调用一定是逻辑写错了
8 树极深导致栈溢出 深度可能到 10510^510​5​​ 时改用迭代

从「会遍历」到「会解题」

到这里，遍历本身已经没什么难的了。但真实的题目不会问你「输出前序序列」，而是会问「这棵树的深度是多少」「翻转它」「路径和等于目标值的路径有几条」。

好消息是：这些题和遍历用的是同一副骨架，差别只在「单层逻辑」那一行填什么。

遍历是骨架，题目是血肉。骨架永远是「终止条件 + 递归左右」，血肉是中间那几行。

例 1：最大深度（后序，靠返回值汇总）

这里返回值承担了「子树把答案告诉父节点」的职责，所以是典型的后序思路。写成一行就是 return max(maxDepth(root->left), maxDepth(root->right)) + 1;

注意 + 1 的位置：它加的是「自己这一层」，这就是递归里那一层自增的来源。

例 3：路径总和（前序，靠参数往下传）

两个值得抄下来的技巧：

  1. 用减法代替「维护一个路径和变量」。每往下走一层，就把当前节点的值从目标里扣掉，走到叶子时只需判断「剩下的目标值是不是正好等于叶子」。这样完全不用管「回溯时把值加回来」这件事——因为参数是按值传递的，每层天然有自己的副本。这是「往下传信息」型递归最常用的写法。
  2. || 短路。左子树找到答案了，右子树就不用再走了，这一行本身就带剪枝。

如果题目改成「收集所有路径」，就得真的维护路径数组，那时候才需要 push_back + pop_back 手动回溯——回溯就是「进入时做选择，离开时撤销选择」，仍然是那两个时刻的用法。

递归的心法

最后几条，是写完上面这些之后我自己总结的：

  1. 不要试图在脑子里展开整棵树。 人脑能同时记住的层级大概就 5～7 层，而递归的展开是二维的。你越用力去「模拟」，越容易乱。真正该做的是验证「当前这一层」是否正确。
  2. 相信子问题已经解决。 写 maxDepth(root->left) 的时候，就当它一定返回了左子树的正确深度。这不是偷懒，这是递归的定义。
  3. 先用最小的例子验证单层逻辑。 一个节点的树、两个节点的树、只有左孩子的树——这三棵树能把 90% 的边界错误暴露出来。
  4. 递归写不出来时，回到三要素。 参数够不够？终止条件是什么？这一层要做什么？绝大多数「写不出来」都是因为这三条里有一条没想清楚，而不是因为不会递归。
  5. 「一看就会，一写就废」是正常的。 递归是一种需要手感的技能，看懂的瞬间和写对的瞬间之间隔着几十道题。这也是为什么我在二叉树基础知识总结那篇里给自己的最后一句提醒是「回到具体题目上手写」。

小结：前中后序只是「同一副骨架里，访问动作插在不同位置」；树和递归之所以绑定，是因为树的定义本身就是递归的，而递归的栈正好替我们保存了「二维结构在一维指针世界里丢失的来路」。想明白这两句话，二叉树的题目就从「背模板」变成了「填骨架」。
